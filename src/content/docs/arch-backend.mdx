The Browy backend is a small Node.js process registered with Chrome /
Edge / Brave as a **native messaging host** under the application id
`com.browy.host`. It runs on your machine.

## Data flow

```
┌───────────────────┐ native msging ┌───────────────────┐ child process ┌───────────────────┐
│ Browser ext       │ ◄───────────► │ Browy host        │ ◄───────────► │ GitHub Copilot    │
│ (sidepanel,       │     port      │ (Node, this       │               │ CLI / SDK         │
│  devtools panel)  │               │  doc)             │               │ (LLM bridge)      │
└───────────────────┘               └───────────────────┘               └───────────────────┘
                                              │
                                              ▼
                                    ┌───────────────────┐
                                    │ CDP via           │
                                    │ chrome.debugger   │
                                    │ (executed back in │
                                    │  the extension)   │
                                    └───────────────────┘
```

The extension speaks to the host over a single bidirectional
length-prefixed JSON channel (Chrome's native messaging protocol).
The agent's tools run in the host. When a tool needs the page, the
host sends the extension a `cdp.send` message (or `tab.new`,
`tab.activate`, `tab.list`, `tab.getActive`); the extension's service
worker runs it through `chrome.debugger` or `chrome.tabs` and posts a
`tool.result` back.

## Lifecycle of a single message

1. User types in the side panel and hits send.
2. The side panel posts `{type: 'chat.send', sessionId, text}` to
   the service worker, which forwards it over the native port.
3. Host's `Runner` binds the agent to that session id and calls
   `agent.chat(text)`. If no Copilot session is open for the id, the
   agent calls the SDK's `resumeSession(id, ...)` (or
   `createSession({sessionId: id, ...})` the first time) with the
   filtered tool list, then sends your text with the current tab's
   context and a fresh page snapshot attached.
4. The SDK streams events back. Host forwards text chunks as
   `{type: 'chat.delta'}`. When the SDK calls a tool, the host posts
   `{type: 'chat.tool_call'}` to the panel, runs the tool, then posts
   `{type: 'chat.tool_result'}`.
5. Each CDP command the tool needs goes to the extension as
   `{type: 'cdp.send', sessionId, callId, method, params}`
   (`inspect_page`, for example, is one `Runtime.evaluate`). The
   service worker runs it with `chrome.debugger.sendCommand` and
   posts `{type: 'tool.result', sessionId, callId, ok, result}`.
6. Host hands the tool's result back to the SDK; the loop continues
   until the SDK reports `session.idle`.
7. Host posts `{type: 'chat.done', sessionId, text}`.

The whole exchange is synchronous from the model's perspective; from
the user's perspective it streams in real time.

## Sessions and persistence

Browy delegates session storage to the GitHub Copilot CLI's session
machinery (in `~/.copilot/`). The host uses the id the extension
mints for a chat (`sp-…` in the side panel, `dt-…` in the DevTools
panel) as the Copilot session id. The extension keeps the current one
in `chrome.storage.local`, so reopening a panel resumes the same
Copilot session.

The agent also has its own scratch surfaces:

- `~/.browy/data/files/`: sandboxed file scratch the `save_file` /
  `read_file` agent tools operate against
- `~/.browy/data/notes.json`: persistent key-value memory across chats
- `~/.browseragent/native-host.log`: single rotating 5 MB log file

## Tool dispatch

Tool definitions live in `src/agent/tools/browser.ts`. Each one
declares:

- `def`: `name`, `description`, JSON-schema `parameters` (consumed by the SDK)
- `run(args, ctx)`: runs in the host. Browser tools call
  `ctx.cdp.send(method, params)`; `src/agent/extension-context.ts`
  sends each call to the extension as a `cdp.send` message and awaits
  the matching `tool.result` reply

This means the tool logic runs in the host, and only the CDP commands
run in the extension, where the page lives. Tools like `save_file`,
`note_set` and `run_script` run entirely in the host. The host is the
orchestrator and the bridge to the LLM.

`src/agent/loop.ts` wraps each tool with the SDK's `defineTool` and
builds the tool list when it creates or resumes a Copilot session.
`toolPolicy()` in `src/agent/tool-policy.ts` filters it against the
user's [Settings → Tools](/tools/#configurable-per-tool-toggles)
toggles, which the extension sends with every `session.start`. A tool
you switch off is dropped from the definitions and from the SDK's
`availableTools` allowlist, and the opt-in host tools stay out until
you switch them on.

## Logging & rotation

`src/native-host.ts` rebinds `console.*` so it writes to
`~/.browseragent/native-host.log` as well as stderr. When the host
starts and the file is over ~5 MB, it is renamed to
`native-host.log.1` and a fresh one begins. Only one old copy is
kept; the next rotation overwrites it.

This is the first place to look when a session misbehaves. It contains
the host's diagnostic output, not transcripts.
